# Skill Home 技能目录版本号设计

## 1. 目标

为 Skill Home 增加一个可以被客户端轮询的“技能目录版本号”，让本地客户端能够快速判断当前缓存的公开 skill 目录结构是否已经过期。

期望的用户可见结果是：

- 服务端提供一个轻量接口，只返回技能目录版本信息
- 客户端不必每次都重新拉完整的 skill 列表
- 当公开目录结构发生变化时，版本号会单调递增
- 当 skill 列表没有变化时，客户端可以继续使用本地缓存

这样可以把“是否需要刷新列表”和“真正下载列表内容”拆成两个成本完全不同的请求。

## 2. 现状

当前 Skill Home 提供了：

- `GET /api/v1/skills` 用于返回公开 skill 列表
- `GET /api/v1/search` 用于按关键词查询公开 skill
- 多个写操作接口用于创建、更新、删除 skill 以及发布、删除版本

但当前服务端没有任何“列表元版本”概念。

这意味着客户端如果想知道远端 skill 列表是否变化，只能：

- 每次重新拉取完整列表
- 或者依赖本地猜测和固定刷新周期

这会带来几个问题：

- 列表轮询成本高于必要水平
- 客户端缓存策略不容易收敛
- 后续如果列表规模继续增长，重复拉全量列表的收益会越来越差

## 3. 设计决策

采用“单调递增整数版本号”的方式表达技能目录版本，而不是时间戳。

### 3.1 核心决策

服务端新增只读接口：

- `GET /api/v1/catalog/version`

返回结构：

```json
{
  "catalog_version": 1,
  "updated_at": "2026-03-30T09:15:00Z"
}
```

语义约定：

- `catalog_version` 是客户端判断目录结构缓存是否过期的唯一权威字段
- `updated_at` 只用于排障、观测和日志，不参与缓存命中判断
- 该版本号只覆盖公开目录结构与可见性相关变更，不覆盖 `download_count`、`rating`、`rating_count` 等动态统计字段

### 3.2 为什么不用时间戳

时间戳虽然看起来更直观，但不适合作为缓存版本号协议：

- 它不是天然表达“第几次变化”
- 不同数据库和序列化精度可能引入比较歧义
- 删除记录时如果靠 `max(updated_at)` 推导，会出现版本回退风险

单调递增整数更适合客户端使用：

- 只需要做整数比较
- 不依赖时区
- 不依赖时间精度
- 更容易验证“写操作成功后版本一定变化”

## 4. 范围

### 4.1 本阶段包含

- 新增技能目录状态模型及自动迁移
- 新增 `GET /api/v1/catalog/version`
- 在所有会影响公开目录结构的写操作中递增目录版本号
- 为新增接口和版本递增逻辑补测试

### 4.2 本阶段不包含

- 客户端本地缓存实现
- ETag、If-None-Match 或 HTTP 缓存协商
- 针对搜索结果做单独版本号
- 针对私有 skill 列表做独立版本号

## 5. 哪些操作会触发版本号变化

版本号只在“会影响公开目录结构或可见性元数据”的成功写操作后递增。

本阶段明确包含：

- 创建 skill
- 更新 skill 元数据
- 删除 skill
- 发布 skill 新版本
- 删除 skill 版本

本阶段明确不包含：

- 下载 skill
- 用户登录
- API key 管理
- 评分与评论
- 审计日志写入

这里的原则是：只有会改变客户端用于安装、搜索、筛选和浏览的公开目录结构时，才应 bump。
像 `download_count`、`rating`、`rating_count` 这类动态统计字段不纳入本阶段版本号语义，客户端如果关心这些字段的新鲜度，应主动重新请求列表或详情接口。

## 6. 数据模型

新增一张独立的小表，例如：

- `skill_catalog_states`

表中只维护一行目录状态记录，包含：

- `catalog_version`
- `updated_at`

建议结构语义为：

- 主键固定为单例行
- `catalog_version` 从 `1` 开始
- 每次有效写操作成功提交时，执行原子自增

之所以用独立表，而不是把这个状态塞进现有 `skills` 或 `audit_logs`：

- 能避免把缓存协议耦合到业务表扫描
- 不需要通过聚合推导版本
- 能保证删除 skill 时版本不会回退
- 后续扩展“别的全局版本号”时也有清晰落点

## 7. 服务端行为

### 7.1 读取接口

`GET /api/v1/catalog/version` 应为公开只读接口，不要求登录。

返回内容只包含：

- 当前 `catalog_version`
- 对应的 `updated_at`

如果表还没有初始化记录，服务端应返回自动初始化后的默认值，而不是返回空结果。

### 7.2 写操作递增

以下处理器在成功事务内都要 bump 目录版本：

- `CreateSkill`
- `UpdateSkill`
- `DeleteSkill`
- `PublishVersion`
- `DeleteVersion`

递增动作必须放在各自现有数据库事务内部，和业务写入一起提交。

这样可以保证：

- 如果业务事务失败，版本号不会误增
- 如果接口返回成功，版本号一定已经变化

### 7.3 原子性要求

版本号递增必须是原子操作。

推荐形式是数据库级别的：

- `catalog_version = catalog_version + 1`

而不是：

1. 先读当前值
2. 再在应用层 `+1`
3. 再写回

后者在并发发布或并发更新时容易丢增量。

## 8. 初始化策略

自动迁移完成后，系统需要确保目录状态表存在一条初始记录。

推荐策略：

- 在启动时完成自动迁移
- 每次读取或 bump 版本号前，调用一个轻量的 “ensure state exists” 辅助逻辑
- 如果记录不存在，则创建默认行，初始 `catalog_version = 1`

这样可以兼容：

- 新环境首次启动
- 已有旧库升级后首次访问新接口

## 9. API 契约

### 9.1 请求

```http
GET /api/v1/catalog/version
```

### 9.2 成功响应

```json
{
  "catalog_version": 12,
  "updated_at": "2026-03-30T09:15:00Z"
}
```

### 9.3 错误响应

沿用现有统一错误格式，例如：

```json
{
  "code": "INTERNAL_ERROR",
  "message": "..."
}
```

## 10. 客户端使用方式

客户端本地维护一个最近一次已知的 `catalog_version`。

刷新流程为：

1. 先请求 `/api/v1/catalog/version`
2. 取到远端 `catalog_version`
3. 如果与本地一致，则跳过全量 skill 列表刷新
4. 如果不一致，则重新请求 `/api/v1/skills` 或对应搜索接口
5. 刷新成功后，更新本地保存的版本号

这个接口只负责告诉客户端“值有没有变”，不负责替代列表接口本身。

## 11. 异常处理

预期行为如下：

- 如果状态表记录缺失，应自动补初始化，而不是返回 404
- 如果业务事务失败，不应 bump 版本号
- 如果 bump 版本号失败，整个写操作应视为失败并回滚
- 如果客户端拿到的目录版本号变化了，但列表拉取失败，客户端不应更新本地缓存版本

## 12. 测试策略

### 12.1 接口测试

- 验证 `GET /api/v1/catalog/version` 能返回初始版本
- 验证响应结构稳定，包含 `catalog_version` 和 `updated_at`

### 12.2 写操作测试

分别验证以下操作成功后版本号会递增：

- 创建 skill
- 更新 skill
- 删除 skill
- 发布版本
- 删除版本

### 12.3 回滚测试

- 构造失败写操作，验证版本号不会误增
- 构造重复发布版本等冲突场景，验证失败时版本号保持不变

### 12.4 并发测试

- 模拟两个并发写操作
- 验证最终版本号递增次数与成功事务数一致

## 13. 受影响代码区域

主要涉及：

- `skill-home-server/internal/models/`
- `skill-home-server/internal/storage/database.go`
- `skill-home-server/cmd/server/main.go`
- `skill-home-server/internal/api/handlers/skill.go`

如果把目录状态辅助逻辑拆到单独文件，还会新增一个小的 handler/helper 文件。

## 14. 取舍

优点：

- 客户端刷新策略更高效
- 版本语义稳定，适合缓存判断
- 服务端实现简单，不依赖大表聚合
- 并发下也能保持单调递增

代价：

- 需要新增一张小表
- 每个会影响目录的写操作都要额外做一次原子更新
- 需要明确哪些业务操作属于“应当 bump 目录版本”的范围

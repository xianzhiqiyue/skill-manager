# Skill Home 标签与评分轻闭环设计

## 1. 目标

为 Skill Home 的 Web 详情页补齐一条低门槛的“社区认知 + 用户反馈”轻闭环，让用户在浏览 skill 详情时既能快速理解这个 skill 常被拿来做什么，也能顺手留下对它的主观评价。

期望的用户可见结果是：

- 进入 skill 详情页后，优先看到社区如何给这个 skill 贴场景标签
- 已登录用户可以直接在详情页补充社区标签
- 已登录用户可以直接在详情页打分，并可选填写一句短评
- 列表页能展示评分信号，帮助用户更快判断是否值得点进详情
- 官方 tags 继续承担稳定分类职责，社区 tags 主要承载共建场景语义

本设计聚焦“让功能先被用起来”，不试图一步到位做成复杂的评价系统或标签治理系统。

## 2. 现状

当前 Skill Home 已经具备两块底层能力：

- 官方 tags 会随 skill 创建与编辑一起写入，并可用于公开列表和搜索筛选
- 社区 tags 已支持在详情页按用户增删，接口会返回聚合后的 `community_tags` 与当前用户的 `viewer_tags`
- 评分接口已在 server 和 CLI 中打通，服务端支持 1-5 分、可选评论，并且会回算 `rating` 与 `rating_count`

但当前 Web 端还没有形成真正的使用闭环：

- 详情页虽然已经展示社区 tags，但位置偏后，更像附加信息
- Web 端没有显眼的评分入口，评分能力主要停留在 CLI
- 列表页虽然支持“高评分”排序，但结果项自身几乎不展示评分信号
- 官方 tags、社区 tags、评分三者之间还没有形成清晰的角色分工

这会导致两个问题：

- 用户能看到这些能力存在，但缺少明确的参与动机
- 列表页即使消费了部分数据，也不够解释“为什么我该点开这个 skill”

## 3. 设计决策

本次采用“详情页双信号轻闭环”方案。

### 3.1 核心决策

以 skill 详情页作为唯一的用户贡献主战场：

- 社区 tags 站前台，回答“这个 skill 通常被拿来做什么”
- 评分作为紧随其后的信任信号，回答“这个 skill 靠不靠谱”
- 官方 tags 不退出，但退回到“官方信息”角色，保持筛选与稳定分类职责

### 3.2 为什么选择详情页而不是安装后触发

用户已经明确选择第一版以详情页为触发点，而不是安装后或延迟触发。

详情页触发更适合当前阶段：

- 覆盖面最大，不依赖安装链路完整闭环
- 改动主要集中在现有 Web 页面的信息架构和交互层
- 对已有 server/CLI 能力复用最高
- 更容易快速验证社区标签和评分是否真的有人愿意留下

它的缺点是信号会比“安装后评价”更浅，但在当前阶段，这种低门槛比高可信度更重要。

### 3.3 为什么社区 tags 要站前台

本次特意选择让社区 tags 站前台，而不是官方 tags。

原因是：

- 官方 tags 更像作者声明，适合稳定分类，不适合强调社区共建感
- 社区 tags 更能表达使用场景、任务语义和真实语境
- 让社区 tags 成为详情页第一信号，能更自然地带出“我也可以补一个标签”

但为了避免目录系统失控，第一版仍不把社区 tags 直接并入全站筛选主轴。

### 3.4 评分权限

评分权限采用“登录即可评分”的低门槛策略：

- 只要登录并进入详情页，就可以提交评分
- 不要求已安装、已下载或已执行
- 允许修改已有评分

这是有意的取舍：

- 优点是能更快积累评分样本，拉起 `rating_count`
- 缺点是评分可信度弱于“安装后评分”

本阶段优先解决“没有信号”的问题，而不是过早优化“信号只来自强使用者”。

## 4. 范围

### 4.1 本阶段包含

- 调整详情页信息层级，让社区 tags 提前
- 为 Web 端新增评分提交能力
- 在详情页展示用户当前评分、平均分和评分人数
- 在列表结果项展示评分信号
- 保留官方 tags 的筛选职责
- 为新增交互补充前端测试
- 更新设计文档与实施计划文档

### 4.2 本阶段不包含

- 仅允许安装后评分
- 评论列表、评论排序、评论审核
- 社区 tags 直接参与公开列表筛选
- 社区 tags 的治理后台、合并规则、别名系统
- 推荐算法、综合热度分、多因子加权排序

## 5. 用户体验设计

### 5.1 详情页信息顺序

详情页主内容区调整为以下顺序：

1. 社区标签卡片
2. 评分卡片
3. What this skill does
4. Install
5. Activity

这样用户在阅读功能说明前，就能先看到两个决策信号：

- 这是个什么场景下常用的 skill
- 它目前是否得到过正向反馈

### 5.2 社区标签交互

社区标签区的目标是让用户用最低成本补充“场景语义”。

具体交互：

- 未登录用户：
  - 可查看社区 tags
  - 显示“登录后可补充社区标签和评分”
- 已登录用户：
  - 继续显示聚合后的社区 tags
  - 可在同区块输入一个标签并提交
  - 可移除自己已添加的标签

交互反馈保持当前轻量风格：

- 添加成功后原地刷新详情模型
- 移除成功后原地刷新详情模型
- 错误只在卡片内部提示，不做全局打断
- 重复标签沿用后端幂等行为，不额外制造“失败感”

### 5.3 评分交互

评分卡片位于社区标签卡片之后，承担“看完别人怎么理解它，再表达我怎么看”的角色。

具体交互：

- 未登录用户：
  - 可看到均分和评分人数
  - 点击评分入口时跳登录
- 已登录用户：
  - 直接看到 1-5 星评分入口
  - 可以只打分，不写评论
  - 可以补一句简短评论
  - 若已评分，则回显当前用户评分，并允许再次修改

提交成功后应原地显示：

- 当前用户评分
- 最新均分
- 最新评分人数

第一版不展示评论流，也不展示他人的评论详情。

## 6. 信息职责分工

### 6.1 官方 tags

官方 tags 的角色是：

- 目录稳定分类
- 列表筛选与检索辅助
- 作者声明 skill 的核心定位

它们应继续存在，但不再承担详情页第一视觉重心。

### 6.2 社区 tags

社区 tags 的角色是：

- 补充使用场景
- 表达社区如何理解这个 skill
- 形成轻量共建氛围

社区 tags 第一版只在详情页重点展示，不直接升级为列表筛选主轴。

### 6.3 评分

评分的角色是：

- 为列表页提供一个快速可信度参考
- 为详情页提供即时反馈与参与动机
- 支撑“高评分”排序的可解释性

评分人数低时应弱化表达，避免伪造强信号。

## 7. 列表页消费策略

列表页不承担主要输入职责，只负责消费信号并帮助判断。

### 7.1 列表结果项

每个结果项应展示：

- 均分
- 评分人数
- 结果项已有的核心元信息

社区 tags 在第一版不强制加入列表结果项主布局，以免结果密度过高；列表仍优先展示官方 tags。

### 7.2 排序解释性

由于列表已经支持 `rating` 排序，结果项必须把评分显示出来，否则用户无法理解“高评分”排序依据。

### 7.3 弱信号处理

对于 `rating_count = 0` 的 skill：

- 显示“暂无评分”或类似弱提示
- 不把它包装成负面状态

对于评分人数很少但有评分的 skill：

- 通过“X 人评分”保留背景信息
- 不额外做复杂可信度算法

## 8. 技术实现边界

### 8.1 服务端

本阶段尽量不改动服务端协议设计。

原因是当前 server 已具备：

- 社区 tags 的读取与写入
- 评分写入与聚合
- 详情返回 `user_rating`

因此服务端侧无需新增复杂能力，只需要前端正确消费现有响应结构。

### 8.2 Web 端

Web 端是本阶段主实现面：

- `api.ts` 需要补齐评分相关类型和请求函数
- `useRegistryApp.ts` 需要新增评分状态和提交逻辑
- `SkillOverviewPage.tsx` 需要新增评分卡片并调整信息顺序
- 搜索结果组件需要展示评分信号

## 9. 测试策略

本阶段以前端行为测试为主，至少覆盖：

- 已登录用户在详情页提交评分
- 未登录用户点击评分入口的处理
- 已有 `user_rating` 时的回显与二次修改
- 社区 tags 区仍能正常添加与移除
- 列表页结果项显示均分与评分人数
- 无评分 skill 的文案和展示分支

## 10. 风险与后续演进

### 10.1 已知风险

- 低门槛评分可能导致评分样本噪声较高
- 社区 tags 如果未来进入筛选，会面临别名和同义词治理问题
- 详情页信号变多后，信息密度需要靠布局控制

### 10.2 后续可演进方向

如果第一版跑通并且数据开始积累，下一阶段可考虑：

- 增加“已安装/已使用”标记，提升评分可信度
- 把高质量社区 tags 上升为可检索维度
- 展示短评摘要或最新评论
- 为低评分或已弃用 skill 增加更明确风险提示

## 11. 结论

本设计的核心不是把 Skill Home 做成完整应用商店，而是用最小改动让两类已有能力真正进入用户路径：

- 社区 tags 负责“找得到”
- 评分负责“敢使用”

通过把它们前置到详情页、并让列表页消费评分信号，Skill Home 可以先形成一条低摩擦、可持续迭代的社区反馈闭环。

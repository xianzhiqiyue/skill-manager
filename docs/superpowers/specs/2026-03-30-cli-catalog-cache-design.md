# `skill-home` 命令行目录缓存设计

## 1. 目标

为 `skill-home` 命令行工具增加一层轻量的“远程目录缓存”，让以下两个命令在常规场景下减少全量拉取，在远端临时失败时也能优雅回退：

- `skill-home list --remote`
- `skill-home search`

期望用户可见结果是：

- 当远端公开目录结构没有变化时，命令行工具直接复用本地缓存结果
- 当远端公开目录结构发生变化时，命令行工具自动刷新缓存
- 当远端临时失败但本地已有缓存时，命令行工具自动回退到旧缓存，并明确提示“结果可能过期”
- 当本地没有缓存且远端失败时，命令行工具仍然明确报错

本次设计同时更新 `skill-home-manager` 这个 Codex 技能的说明，让它能正确描述新的命令行行为。

## 2. 背景

当前 `skill-home` CLI 已经具备：

- `GetCatalogVersion()`：读取远端 `GET /api/v1/catalog/version`
- `list --remote`：直接请求远端公开技能列表
- `search`：直接请求远端搜索接口

但当前命令层还没有真正利用 `catalog_version`：

- 每次 `list --remote` 都重新请求远端列表
- 每次 `search` 都重新请求远端搜索结果
- 远端短暂失败时，命令行工具没有旧缓存可回退

与此同时，服务端已经收窄了 `catalog_version` 的语义：

- 它只覆盖公开目录结构相关变更
- 不覆盖 `download_count`、`rating`、`rating_count` 等动态统计字段

因此，命令行工具的缓存语义也必须保持一致，不能把它包装成“所有列表字段都一定最新”的强保证。

## 3. 核心设计

### 3.1 缓存范围

本阶段只给以下两个命令接入目录缓存：

- `skill-home list --remote`
- `skill-home search`

本阶段不扩展到：

- `info`
- `list-versions`
- `pull/install/update`
- 任何写操作命令

### 3.2 语义边界

命令行工具只把 `catalog_version` 视为“公开目录结构缓存”的权威字段。

这意味着：

- 当 `catalog_version` 未变化时，命令行工具可以复用本地缓存的列表和搜索结果
- 命令行工具不承诺缓存里的 `download_count`、`rating`、`rating_count` 是最新值
- 如果用户关心这些动态统计字段的新鲜度，本阶段唯一可靠来源仍然是未缓存的详情读取链路；`list --remote` 与 `search` 不保证这些字段实时

### 3.3 失败回退策略

当远端失败时，行为固定为：

1. 如果本地存在“属于当前注册中心且状态一致”的对应缓存，则自动回退
2. 命令行工具输出明确提示，例如“已使用本地缓存，结果可能过期”
3. 如果本地不存在对应缓存，则保持当前错误行为，直接报错

这个策略同时适用于：

- 目录版本检查失败
- 刷新列表请求失败
- 刷新搜索请求失败

## 4. 缓存结构

缓存文件放在 CLI 配置目录下，不放进本地 skill 安装目录。

建议目录：

- `~/.config/skill-home/cache/remote-catalog/<注册中心哈希>/`

包含两类文件：

### 4.1 全局状态文件

文件：

- `state.json`

字段建议：

- `registry_endpoint`
- `catalog_version`
- `checked_at`
- `updated_at`

说明：

- `registry_endpoint` 用于记录当前缓存所属的注册中心来源
- `catalog_version` 表示当前缓存对应的远端目录版本
- `checked_at` 表示最近一次成功校验目录版本的时间
- `updated_at` 对应远端接口返回的目录更新时间，仅用于观测

### 4.2 查询结果文件

目录：

- `queries/`

每个查询结果一个文件，key 至少包含：

- `registry_endpoint`
- 命令类型：`list` 或 `search`
- `namespace`
- `query`
- `tags`
- `page`
- `per_page`

建议做法：

- 先构造稳定的 JSON key
- 再取哈希值作为文件名

这样即使用户切换了 `registry.endpoint`，不同注册中心的同一查询也不会落到同一缓存命名空间。

查询结果文件中保存：

- `registry_endpoint`
- 原始结果对象
- 对应 `catalog_version`
- 缓存写入时间

## 4.3 状态文件与查询文件的一致性

`state.json` 与查询结果文件都需要自描述，但它们承担的职责不同：

- `state.json` 表示“当前注册中心最近一次成功校验到的目录版本”
- 查询结果文件表示“某个具体查询在某次目录版本下的结果快照”

因此，必须把“新鲜命中”和“失败回退”分开定义，不能用同一套条件同时处理两种场景。

读取“新鲜缓存”时，至少满足以下条件才允许直接命中：

- `state.json` 存在
- 当前查询结果文件存在
- 两者的 `registry_endpoint` 都与当前命令行配置一致
- 两者的 `catalog_version` 一致
- 两者的 `catalog_version` 都等于刚取到的远端 `catalog_version`

如果任一条件不满足，则视为“无法确认缓存仍然新鲜”，不可直接命中。

当远端失败时：

- 只要求当前查询结果文件自描述完整，且属于当前注册中心
- 即使该查询缓存落后于 `state.json` 记录的较新目录版本，也允许作为“过期结果”回退
- 如果查询结果文件缺少来源信息或结构不完整，则宁可报错，也不要回退到来源不明的数据

写入缓存时建议使用临时文件加原子替换。

推荐顺序：

1. 先写查询结果文件临时文件并替换
2. 再写 `state.json` 临时文件并替换

如果写入在中途失败，下次读取会因为版本或来源校验失败而自动放弃“新鲜命中”；只有查询结果文件本身完整且来源可信时，才允许作为“过期结果”回退。

## 5. 命令行行为

### 5.1 `list --remote`

读取流程：

1. 构造查询 key
2. 读取当前注册中心目录下的 `state.json` 和当前查询缓存
3. 请求 `GetCatalogVersion()`
4. 如果远端 `catalog_version` 与本地一致，且当前查询缓存经过“新鲜命中”校验，则直接返回缓存结果
5. 如果远端 `catalog_version` 不一致、当前查询缓存不存在，或当前查询缓存未通过新鲜命中校验，则请求真实 `ListSkills`
6. 请求成功后刷新 `state.json` 与当前查询缓存
7. 如果任一步远端请求失败，但本地已有“属于当前注册中心且自描述完整”的当前查询缓存，则回退并提示“结果可能过期”
8. 如果没有缓存，则报错

### 5.2 `search`

行为与 `list --remote` 一致，只是实际拉取使用 `Search`。

差异点仅在 query key 的组成中包含：

- `query`
- `tags`

### 5.3 输出提示

默认表格输出下：

- 命中缓存且目录版本未变化时，不强制额外提示
- 只有在“远端失败 -> 回退旧缓存”时，输出明确提示

JSON 输出下：

- 不修改原结果结构
- 回退提示仍走 stderr 或普通提示输出，不污染 JSON 主体

## 6. 代码结构建议

建议在命令行工具内新增一层很薄的缓存模块，而不是把逻辑直接散落在 `list.go` 和 `search.go`。

建议新增职责：

- 目录缓存状态读写
- 查询缓存 key 构造
- 目录版本检查
- 带回退的读取流程封装

命令层只负责：

- 解析参数
- 调缓存层获取结果
- 渲染输出

这样后续如果要扩展：

- `info`
- 缓存清理命令
- 更细粒度的缓存生存时间或强制刷新

都可以在现有结构上继续演进。

## 11. 搜索缓存的额外说明

`search` 与 `list --remote` 共用同一个目录版本判断，但两者的正确性边界不同。

本设计只保证：

- 搜索结果来自同一份公开目录快照

本设计不保证：

- 当服务端搜索排序、分词、召回或打分逻辑变化，而目录结构未变化时，缓存搜索结果与当前远端完全一致

因此，`search` 的缓存语义应理解为“基于当前目录快照的搜索结果缓存”，而不是“与当前服务端搜索实现完全一致的强保证”。

# 控制台 API Key 生成功能设计

## 1. 背景

当前控制台已经支持登录后查看和管理我的技能，但还没有 API Key 的前端入口。

现状拆分如下：

- 前端控制台目前只有一个 `/console` 单页，核心任务是技能列表 + 技能详情编辑。
- 后端已经具备 API Key 数据模型、创建接口、撤销接口和鉴权能力。
- 后端当前缺少“列出我的 API Key”接口，因此前端无法展示已有 key 列表。

这意味着该功能不是从零开始，而是“后端已有生成/撤销底座，前端和列表接口缺失”的补全型需求。

## 2. 设计目标

- 在控制台中新增 API Key 的可发现入口，不打断现有技能管理主流程。
- 支持 API Key 的查看、生成、复制、撤销。
- 清楚表达安全边界：完整 key 只展示一次，之后只展示前缀和元数据。
- 保持现有控制台的工具属性，优先信息清晰、操作明确，而不是做成营销式页面。
- 为后续扩展预留空间，例如权限范围、使用统计、最后使用来源。

## 3. 非目标

- 本期不做 API Key 权限范围(scope)设计。
- 本期不做 API Key 编辑/重命名。
- 本期不做按项目分组、按环境分组、按标签筛选。
- 本期不做审计日志独立页面。

## 4. 现状约束

### 4.1 前端约束

- 当前控制台 UI 结构固定为左侧账号/技能列表，右侧技能管理详情。
- 路由仅支持 `/console`，没有控制台子页概念。
- 状态集中在 `useRegistryApp.ts`，功能继续堆叠会让单 hook 和单页面继续膨胀。

### 4.2 后端约束

- 已有 `POST /api/v1/user/api-keys`。
- 已有 `DELETE /api/v1/user/api-keys/:id`。
- 缺少 `GET /api/v1/user/api-keys`。
- 完整 key 只在创建响应中返回一次，这是正确的安全边界，应保留。

## 5. 信息架构

### 5.1 推荐方案

将控制台拆成两个子区域：

- `控制台 / 技能`
- `控制台 / API Keys`

推荐使用子路由而不是仅靠本地 tab 状态：

- `/console/skills`
- `/console/api-keys`

理由：

- 支持刷新后保持上下文。
- 支持从文档或成功提示深链到指定子页。
- 避免把“技能管理状态”和“API Key 管理状态”混在同一视图状态机里。

### 5.2 页面布局

控制台保留现有两栏结构，但左栏从“纯技能侧栏”升级为“账号导航 + 内容入口”：

- 左侧：
  - 用户资料卡
  - 控制台导航
  - 技能概览统计
  - API Key 概览统计
- 右侧：
  - 根据当前子页切换内容
  - `技能` 子页保留现有技能编辑体验
  - `API Keys` 子页展示生成与管理功能

## 6. API Key 页面结构

### 6.1 页面目标

让用户在一个页面内完成三件事：

- 了解 API Key 的用途和安全规则
- 生成新的 API Key
- 管理已有 API Key

### 6.2 页面模块

建议按从上到下的顺序排列：

1. 页面头部
2. 生成区
3. 一次性展示区
4. 现有 Key 列表

### 6.3 页面头部

内容：

- 标题：`API Keys`
- 说明：`为 CLI、自动化任务或第三方集成生成访问凭证。完整密钥仅在创建后展示一次。`
- 辅助说明：JWT 适合浏览器登录态，API Key 适合脚本、CI、远程调用。

头部右侧可放一个安静型帮助入口：

- `查看接入示例`

## 7. 生成区设计

### 7.1 生成表单字段

V1 建议只保留两个字段：

- `名称`
- `过期时间`

其中过期时间建议做成预设分段按钮，而不是先上复杂日期控件：

- 永不过期
- 7 天
- 30 天
- 90 天

如果后续确实需要，再补“自定义日期”。

### 7.2 生成区交互

- 主按钮：`生成 API Key`
- 提交中：按钮变为 `生成中...`
- 成功后：
  - 清空表单
  - 刷新列表
  - 打开一次性展示卡片
- 失败后：
  - 在生成区顶部显示错误 banner

### 7.3 一次性展示区

创建成功后，不用 toast 代替核心结果，而是在页面内插入高优先级成功面板：

- 标题：`请立即保存这串密钥`
- 完整 key 使用等宽字体展示
- 提供 `复制` 按钮
- 提供 `我已保存` 按钮，点击后收起
- 辅助文案：`离开或关闭后将无法再次查看完整内容`

该面板优先级应高于列表，但不要用模态强行打断；内联成功面板更适合桌面控制台工作流。

## 8. 列表区设计

### 8.1 列表字段

每个 API Key 展示：

- 名称
- 前缀
- 创建时间
- 最近使用时间
- 过期时间
- 状态
- 操作

状态建议统一成：

- `可用`
- `即将过期`
- `已过期`

“即将过期”建议定义为 7 天内到期。

### 8.2 列表形式

桌面端使用表格/高密度行列表，移动端切换为卡片。

桌面表头建议：

| 名称 | 前缀 | 创建时间 | 最近使用 | 过期时间 | 状态 | 操作 |

前缀展示格式建议：

- `sk_abcd...`

不展示完整 key，也不展示 hash。

### 8.3 行操作

V1 只保留一个危险操作：

- `撤销`

点击后弹出确认：

- 标题：`撤销 API Key`
- 文案：`撤销后依赖该密钥的脚本和集成会立即失效。`
- 按钮：`取消` / `确认撤销`

撤销成功后：

- 从列表移除该 key
- 显示成功反馈

## 9. 空态与异常态

### 9.1 首次空态

当用户还没有 API Key 时：

- 标题：`还没有 API Key`
- 说明：`先生成一把用于 CLI、自动化任务或第三方集成的访问密钥。`
- CTA：`生成第一把 Key`

### 9.2 加载态

- 生成区保留可见
- 列表区显示 skeleton 或紧凑 loading panel

### 9.3 错误态

错误应分层：

- 列表加载失败：列表区内错误面板 + 重试按钮
- 创建失败：生成区顶部 banner
- 撤销失败：行级失败提示或页内 banner

## 10. 后端接口设计

### 10.1 保留现有接口

- `POST /api/v1/user/api-keys`
- `DELETE /api/v1/user/api-keys/:id`

### 10.2 新增接口

新增：

- `GET /api/v1/user/api-keys`

返回结构建议：

```json
[
  {
    "id": "uuid",
    "name": "CI deploy",
    "prefix": "sk_abcd12",
    "last_used_at": "2026-03-26T10:00:00Z",
    "expires_at": "2026-06-26T10:00:00Z",
    "created_at": "2026-03-26T09:00:00Z"
  }
]
```

V1 不建议后端返回完整状态字段，前端可按时间派生：

- `active`
- `expiring_soon`
- `expired`

## 11. 前端状态设计

建议在 `useRegistryApp` 中新增独立状态组：

- `apiKeys`
- `apiKeysLoading`
- `apiKeysError`
- `apiKeyCreateLoading`
- `apiKeyCreateError`
- `apiKeyCreateSuccess`
- `revealedApiKey`
- `apiKeyRevokeId`

同时新增一个控制台级别的 section 状态，最好由路由驱动：

- `consoleSection = 'skills' | 'api-keys'`

## 12. 组件拆分建议

当前 `App.tsx` 中的控制台已经比较重，新增 API Key 功能时建议顺手拆出几个组件：

- `ConsoleShell`
- `ConsoleSidebar`
- `SkillsConsolePanel`
- `ApiKeysConsolePanel`
- `ApiKeyCreateForm`
- `ApiKeyRevealPanel`
- `ApiKeyTable`

这样后面继续做“权限范围”“使用统计”“SDK 指引”时不会继续膨胀到单文件。

## 13. 安全与体验原则

- 完整 key 只能在创建成功后展示一次。
- 完整 key 不写入 localStorage，不拼到 URL，不进页面初始化 state。
- 默认展示 prefix，而不是模糊后的整串值。
- 撤销操作必须二次确认。
- 过期时间默认可为空，表示长期有效，但 UI 需要提示长期有效的风险。
- 最近使用时间为空时明确显示 `未使用`，而不是留空。

## 14. 推荐视觉与交互风格

沿用当前控制台的浅色、紧凑、工具型视觉语言，不单独做另一套“安全中心”风格。

但 API Key 子页应有自己更清楚的层次：

- 成功 reveal 面板使用明显但克制的成功色背景
- 危险操作使用红色文本按钮，不默认放主按钮
- 关键内容使用等宽字体，例如 prefix 和一次性展示的完整 key
- 列表信息密度高，但按钮数量少，避免“每行很多操作”

## 15. 推荐实施顺序

### 阶段 1

- 新增 `GET /api/v1/user/api-keys`
- 前端 API 层补齐类型和请求函数

### 阶段 2

- 控制台增加 `Skills / API Keys` 子导航
- 完成 API Key 列表页与空态

### 阶段 3

- 接入创建能力
- 完成一次性 reveal 面板和复制反馈

### 阶段 4

- 接入撤销能力
- 补移动端布局、错误态、状态标签和可用性细节

## 16. 验收标准

- 登录用户可以在控制台中进入 API Key 管理区域。
- 用户可以看到已有 API Key 列表。
- 用户可以创建新的 API Key，并且完整 key 只展示一次。
- 用户可以复制完整 key。
- 用户可以撤销已有 API Key。
- 页面在桌面和移动端都可用。
- 控制台结构不会因为新增 API Key 功能而明显混乱。
